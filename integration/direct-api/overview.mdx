---
title: "Direct API overview"
description: "You host the payment step and handle the one-time code."
---

You collect the mobile number, trigger the code, collect the code, and submit it.

```
Your system                                        Cashd
     │ 1. availability ──────────────────────────►   │
     │ 2. create transaction ────────────────────►   │ ── SMS code ──► customer
     │ 3. submit code ───────────────────────────►   │
     │ ◄──────────────── authorized ─────────────────┤
     ▼
  fulfil
```

Use this option when there is no browser or webview at the payment step — a till,
a kiosk, a call-centre screen — or when the payment interface must stay inside
your own product.

## Sequence

| # | Call | Effect |
|---|---|---|
| 1 | `POST /merchant/availability` | Evaluation only. No state change, no code sent, no charge. |
| 2 | `POST /merchant/transactions` | Creates a transaction awaiting the code and sends the SMS. |
| 3 | `POST /merchant/transactions/:id/confirm` | Verifies the code, debits the wallet, authorises. |
| 4 | `GET /merchant/transactions/:id` | Status retrieval, for reconciliation and unresolved outcomes. |

## What you own

Choosing this option means you own the code experience end to end, including
every failure state.

| You build | Detail |
|---|---|
| Phone entry | Accepting all the formats in [Conventions](/integration/get-started/conventions) |
| Code entry | Countdown, remaining attempts, resend control |
| Failure messages | Arabic and English, right-to-left, for every error |
| Code hygiene | The code must never reach logs, analytics, crash reports, or session replay |

See [Code requirements](/integration/direct-api/otp-requirements). Most of the
build is there, not in the happy path.
