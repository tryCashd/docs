---
title: "Availability"
description: "POST /merchant/availability"
---

Evaluates whether a customer can cover an amount. Nothing changes, no code is sent, nothing is charged. Use it to decide whether to offer Cashd.

```http
POST {base}/api/v1/merchant/availability
Authorization: Bearer tc_live_sk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Content-Type: application/json

{ "phone": "+966501234567", "amount": 12500 }
```

```http
200 OK

{
  "status": "available_full",
  "amount": 12500
}
```

## Outcomes

| `status` | Meaning | Action |
| --- | --- | --- |
| `available_full` | The full amount is coverable | Proceed with the requested amount |
| `unavailable` | The amount is not coverable | Do not offer Cashd. Collect the full amount with another tender |

`amount` echoes the amount you sent. There is no other field.

`unavailable` does not say why. A customer with no Cashd account, an empty wallet, a locked account, and a wallet that covers only part of the amount all return the same response. Supply your own decline copy for the customer and for counter staff.

## Full amount or nothing

Cashd authorises the requested amount in full or not at all. There is no split tender on this rail: you cannot charge part of a basket to Cashd and collect the rest another way within the same transaction. Creating a transaction for an amount the wallet cannot fully cover fails with [`insufficient_balance`](/errors/insufficient_balance).

## Availability is not a reservation

The response reflects a moment in time. Balance can move between this call and the charge, and another transaction can consume it. An [`insufficient_balance`](/errors/insufficient_balance) on the subsequent create is a normal outcome, not an exception — handle it in the flow.

## What is not returned

No balance figure, no program name, no indication of how many loyalty programs are funding the wallet, and no decline reason. You learn only whether the amount you asked about is coverable.
